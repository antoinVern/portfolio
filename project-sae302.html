Développement Réseau SAÉ 3.02 2024

Application Android
Communication TCP/IP

Développement d'une application mobile Android en Java permettant d'établir des communications réseau TCP/IP. L'application agit alternativement en mode serveur (écoute sur port 5000) ou en mode client, avec gestion du multithreading pour ne pas bloquer l'interface utilisateur.

Android Studio Java TCP/IP Socket Multithreading XML UI Gradle ServerSocket

Étape 1

Configuration réseau — AndroidManifest & Gradle

L'accès au réseau sur Android nécessite une déclaration explicite des permissions dans le manifeste. Le projet utilise le Kotlin DSL Gradle comme système de build, ciblant Android 7.0 (API 24) minimum.

1
Permission INTERNET dans AndroidManifest.xml
Sans cette permission, toute tentative d'ouverture de socket lève une SecurityException au runtime. Elle est déclarée au niveau de l'application, avant la balise <application>.
<!-- AndroidManifest.xml --> <uses-permission android:name="android.permission.INTERNET" /> <application android:usesCleartextTraffic="true" <!-- Autoriser HTTP non-chiffré pour les tests LAN --> ... >
Permission réseau déclarée — accès socket autorisé
2
Configuration Gradle (Kotlin DSL)
Configuration du build avec minSdk 24 (Android 7.0) pour une compatibilité maximale avec les appareils récents. Le gestionnaire de dépendances Kotlin DSL remplace Groovy pour une meilleure lisibilité et typage statique.
// build.gradle.kts (app) android { compileSdk = 34 defaultConfig { minSdk = 24 // Android 7.0+ targetSdk = 34 } }
Build configuré — API 24+ ciblée

Étape 2

Serveur TCP — ServerTCP.java

Le serveur écoute les connexions entrantes sur le port 5000 et répond à chaque message reçu par un écho préfixé. Pour ne pas bloquer l'interface utilisateur Android, toute l'écoute est faite dans un Thread dédié.

1
Création du ServerSocket et attente de connexion
Un ServerSocket est créé sur le port 5000, écoutant sur toutes les interfaces réseau. La méthode accept() est bloquante, d'où le thread séparé.
// ServerTCP.java — Lancement du serveur dans un Thread new Thread(() -> { try (ServerSocket serverSocket = new ServerSocket(5000)) { log("Serveur démarré sur port 5000..."); Socket client = serverSocket.accept(); // Attente connexion log("Client connecté : " + client.getInetAddress()); BufferedReader in = new BufferedReader(new InputStreamReader(client.getInputStream())); PrintWriter out = new PrintWriter(client.getOutputStream(), true); String msg; while ((msg = in.readLine()) != null) { log("Reçu : " + msg); out.println("Echo : " + msg); // Réponse au client } } catch (IOException e) { log("Erreur serveur : " + e.getMessage()); } }).start();
Serveur TCP opérationnel — écho sur port 5000

Étape 3

Client TCP — ClientTCP.java

Le client se connecte à un serveur distant à l'IP et au port saisis par l'utilisateur. L'envoi et la réception de messages sont également asynchrones pour garantir la fluidité de l'interface.

1
Connexion et échange de messages
La classe Socket établit la connexion TCP. Les flux d'entrée/sortie sont enveloppés dans des BufferedReader / PrintWriter pour manipuler des lignes de texte.
// ClientTCP.java — Connexion et envoi de message new Thread(() -> { try (Socket socket = new Socket(ipAdresse, port)) { log("Connecté à " + ipAdresse + ":" + port); PrintWriter out = new PrintWriter(socket.getOutputStream(), true); BufferedReader in = new BufferedReader(new InputStreamReader(socket.getInputStream())); out.println(message); // Envoi du message String reponse = in.readLine(); // Lecture de l'écho serveur log("Réponse : " + reponse); } catch (IOException e) { log("Erreur client : " + e.getMessage()); } }).start();
Communication client-serveur bidirectionnelle validée

Étape 4

Interface XML — activity_main.xml

L'interface graphique est conçue en XML Android avec un layout linéaire. Elle offre une prise en main immédiate grâce à des contrôles clairs et une console de logs intégrée.

1
Composants de l'interface
L'UI est divisée en deux zones : Réseau (IP + port + boutons d'action) et Console de log (ScrollView affichant les échanges en temps réel).
  • EditText IP — Saisie de l'adresse IP du serveur cible
  • EditText Port — Saisie du port de connexion (défaut : 5000)
  • Bouton "Démarrer Serveur" — Lance ServerTCP dans un thread
  • Bouton "Connecter" — Lance la connexion ClientTCP
  • Bouton "Envoyer" — Envoie le message saisi
  • Console Logs — ScrollView auto-scroll pour les échanges
Interface dual-mode fonctionnelle sur émulateur

Bilan

Résultats et perspectives

L'application satisfait les critères de base de la SAÉ 3.02 : communication TCP/IP bidirectionnelle fonctionnelle, gestion du multithreading, interface claire. Les tests conduits sur simulateur Android ont validé la stabilité de la connexion.

  • TCP / Sockets : connexion client-serveur stable, échanges de messages validés
  • Multithreading : UI fluide — zéro blocage du thread principal
  • Architecture dual-mode : basculement client/serveur sans redémarrage
  • Écho serveur : préfixe "Echo :" affiché dans la console du client
Perspectives d'amélioration
  • Multithreading serveur — gérer plusieurs clients simultanément avec un thread pool
  • Protocol UDP — implémenter DatagramSocket pour des transferts sans connexion
  • Sérialisation — envoyer des objets Java sérialisés plutôt que de simples chaînes

Analyse réflexive :

💡
Ce que j'ai acquis. Cette SAÉ m'a permis de relier concrètement la couche transport (TCP) à une implémentation logicielle : je comprenais le fonctionnement du protocole en cours, mais écrire un ServerSocket qui accepte une connexion et y répond m'a donné une vision claire du cycle requête-réponse. La gestion du multithreading Android était une contrainte supplémentaire qui m'a obligé à comprendre pourquoi les opérations réseau ne peuvent pas se faire sur le thread UI.
⚡
Principale difficulté. La gestion des exceptions réseau en Java Android est verbeuse. La fermeture correcte des flux (try-with-resources) et la synchronisation entre le thread réseau et le thread UI pour mettre à jour la console de log sans crash ont demandé plusieurs itérations de débogage.
🔄
Ce que je ferais différemment. J'utiliserais Kotlin Coroutines avec les scopes Android plutôt que des Threads Java bruts — la gestion du cycle de vie est plus sûre et le code plus lisible. Je gérerais aussi plusieurs clients côté serveur dès le départ, avec un ExecutorService.
